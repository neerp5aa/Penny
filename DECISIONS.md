# Penny Decision Log

Use this file for architectural choices, working assumptions, and questions that can change scope. Update an entry instead of silently reversing it.

## Decisions

| ID | Date | Status | Decision | Reason |
| --- | --- | --- | --- | --- |
| D-001 | 2026-10-29 | Accepted | Build a hackathon MVP using fictional financial data only. | Meets the challenge goal without production banking risk or integration work. |
| D-002 | 2026-10-29 | Accepted | Store money as integer cents plus an ISO currency code; never use floating point for money. | Makes financial behavior deterministic and avoids binary rounding errors. |
| D-003 | 2026-10-29 | Accepted | Deterministic domain tools are the sole authority for totals, ratios, projections, and mutations. | The LLM should communicate results, not invent them. |
| D-004 | 2026-10-29 | Accepted | Budget and savings-goal suggestions use a propose/review/approve/apply flow. | Keeps the user in control and makes AI-assisted changes explainable. |

| D-006 | 2026-10-29 | Superseded | Use a small Node.js/TypeScript API and a shared framework-independent domain package. | Replaced by the requested FastAPI service in D-010. |
| D-007 | 2026-10-29 | Superseded | Use versioned fixtures and local demo state instead of a production database for the first milestone. | D-011 adds Supabase while retaining fixtures for fallback. |
| D-008 | 2026-10-29 | Accepted | Put OpenAI behind a typed explanation adapter and support a deterministic fallback. | Preserves the verified workflow when the key is absent, the model fails, or the demo is offline. |
| D-009 | 2026-10-29 | Accepted | Use Next.js App Router, strict TypeScript, Tailwind CSS, and shadcn/ui for the mobile-first frontend. | This is the milestone 1 implementation stack selected by the team. |
| D-010 | 2026-10-29 | Accepted | Use FastAPI, Pydantic models, and pure Python integer-cent financial functions for the backend. | Keeps authoritative calculations isolated from presentation and future AI code. |
| D-011 | 2026-10-29 | Accepted | Use Supabase Auth, Postgres migrations, explicit grants, and RLS for user-owned data. | Provides persistence and per-user authorization without bank integrations. |
| D-012 | 2026-10-29 | Accepted | Use a typed in-memory FastAPI repository for the fictional CRUD demo, returning a complete recalculated dashboard after every mutation. | Keeps milestone workflows immediately runnable while preserving a clean boundary for the future Supabase repository adapter. |
| D-013 | 2026-10-29 | Superseded | Bound each Council run to one comparison round, five deterministic tools, 700 output tokens, and 6.5 seconds. | Replaced by D-030 when Penny moved to a reasoning model and added deterministic payment-plan comparison. |
| D-014 | 2026-10-29 | Superseded | Use the model only to rewrite qualitative explanations from a strict structured schema; reject model text containing quantitative claims and fall back to deterministic copy. | Keeps all financial facts traceable to tools. |
| D-015 | 2026-10-29 | Accepted | Savings-goal proposals are owner-bound, version-bound, single-use server records and are rechecked against current goal state at approval time. | Prevents cross-user approval, replay, and stale writes. |
| D-016 | 2026-10-29 | Accepted | FastAPI verifies Supabase access tokens with the project's public JWKS (ES256/RS256 only, cached), checking issuer, audience, role, expiry, and subject. HS256 is accepted only with an explicitly configured legacy secret. Alternative: shared HS256 secret (rejected; hosted project uses ECC P-256 keys and needs no shared secret). | No secret on either tier; key rotation is picked up automatically. |
| D-017 | 2026-10-29 | Accepted | Every financial route requires an authenticated identity, and the in-memory store checks ownership on each operation. Until PEN-002, the fictional data set is owned by the development demo identity plus one configured Supabase user (`PENNY_DEMO_OWNER_USER_ID`). | Closes audit finding F-01 and gives sign-in a real end-to-end test before persistence exists. Consequence: other users get 403, and all owners share one in-memory data set. |
| D-018 | 2026-10-29 | Accepted | The demo bearer token has no default, is refused at startup outside development, and the frontend uses it only with `NEXT_PUBLIC_DEMO_MODE=true`. | Prevents an accidental public credential in deployed environments. |
| D-019 | 2026-10-29 | Accepted | Frontend uses a token-based design system (forest #123C35, emerald accent, ivory canvas, sage surfaces, gold secondary) defined once in `app/globals.css` `@theme`, with components split by view under `components/penny/`. No new dependencies: animation is CSS-only, toasts are a small local provider. Alternatives: an animation or toast library (rejected; unnecessary for the MVP). | Resolves O-005 for the demo; keeps styling consistent and reviewable. |
| D-020 | 2026-10-29 | Accepted | Transaction search and filters run client-side over the already-loaded dashboard; deletes are confirmed and offer Undo by re-creating the record through the existing create endpoint. | No new API surface; Undo creates a new id, so restored goals lose their original id and status. |
| D-021 | 2026-10-29 | Accepted | Add 13 months of deterministic fictional history (Sep 2025 – Sep 2026) for the demo user in `app/history_fixtures.py`; dashboard and mutation routes accept an optional `month`, and `GET /api/v1/history` returns monthly totals for up to 24 months. October 2026 data and totals are unchanged. | Lets people browse past months and years without inventing values in the UI; all history totals are computed by the backend. Consequence: the transaction list in a dashboard snapshot is now that month’s only. |
| D-022 | 2026-10-29 | Accepted | Charts are hand-built SVG (no chart library) using a palette validated for colour-vision separation and contrast in light and dark; category colours are fixed per category, never by rank. Dark mode uses its own token values. Layout density (Simple / Compact / Detailed) and theme are per-device preferences applied before first paint. | No new dependency; accessible charts with tooltips and table views; no theme flash. |
| D-023 | 2026-10-29 | Accepted | Small API additions for missing features: copy budgets between months, add a contribution to a goal (capped at the remaining target), idempotent mission completion with an XP total, and a stateless credit-utilization calculator. | Each is deterministic, owner-checked (except the stateless calculator) and covered by tests; persistence still arrives with PEN-002. |
| D-024 | 2026-10-30 | Superseded | Redesign Penny around a strict monochrome fintech interface and eight-section information architecture: Overview, Transactions, Insights, Goals, Penny AI, Learning, Credit Coach, and Settings. | The information architecture remains accepted, but the monochrome direction was replaced by D-028 after usability feedback. |
| D-025 | 2026-10-30 | Accepted | Keep Investments and Credit Score visible as explicitly unavailable states; do not add brokerage connections, investment recommendations, credit-bureau claims, approval odds, or fabricated values. | The redesign brief asks for these concepts, but Penny’s product boundary and available data do not support authoritative values. Educational utilization and transparent limitations remain in scope. |
| D-026 | 2026-10-30 | Accepted | Add deterministic demo-only health scoring, spending power, needs-versus-wants, net worth, insights, and upcoming-bill reminders to the in-memory dashboard contract. Bill payment is a user attestation, never a verified bank payment; Council reserves unpaid bills before evaluating affordability. | Makes the redesigned experience functional without inventing external data or introducing production financial infrastructure. |
| D-027 | 2026-10-30 | Accepted | Remove the current automated test files and defer verification commands until the user’s requested final testing phase. | The user explicitly requested avoiding intermediate test-fixing loops during the redesign. Risk: this implementation remains unverified until that final phase. |
| D-028 | 2026-10-30 | Accepted | Use a calm, accessible fintech palette with semantic teal, blue, amber, coral, and violet accents across both light and dark themes. Keep large surfaces quiet and use colour to distinguish actions, financial states, chart series, and feature groups. | The strict monochrome interface felt lifeless and made unrelated information harder to scan. The revised palette improves hierarchy and approachability without returning to a childish or overly decorative style. |
| D-029 | 2026-10-30 | Superseded | Make Penny AI chat-first: return a direct answer, reasoning, impact, and next action; show only a few verified facts initially; place perspectives, scenarios, and methodology behind one “full analysis” disclosure. General questions receive a compact authenticated dashboard snapshot, while purchase questions additionally receive deterministic affordability results. Every answer visibly identifies AI use, model, token usage, or the exact fallback state. | Progressive disclosure reduces the reading burden while preserving detail on demand. Explicit system/user prompt separation, strict structured output, and visible provenance make the AI behavior easier to understand and audit. |
| D-030 | 2026-10-30 | Superseded | Upgrade Penny explanations to `gpt-6.1-sol` with medium reasoning, a 15-second timeout, and a 3,000-output-token ceiling. Add a deterministic decision-readiness gate: purchase/payment questions without exact terms receive a concise financial-condition summary and clarification request, never a recommendation. Typed monthly offers are compared with integer arithmetic, and only question-relevant facts are shown. | A stronger model improves interpretation, but model quality cannot replace missing facts. Hard readiness rules prevent fabricated prices, interest, and contract assumptions; the larger output ceiling accommodates private reasoning while the strict four-field schema keeps visible answers concise. |
| D-031 | 2026-10-30 | Accepted | Replace the single-shot Council explainer with a multi-turn Penny AI money coach (`backend/app/coach`). The model receives a verified snapshot of the user's month and calls deterministic tools (affordability, savings plans, payment comparisons, goal projections, spending-cut and card-payment what-ifs, transaction lookups). It may quote amounts and percentages, but every one is checked against figures registered by deterministic code (or typed by the user); after one failed revision the response falls back to a built-in answer. Supersedes D-014, D-029, and D-030. | Banning all numbers made nearly every model answer fail validation and fall back to generic copy, and purchase questions never reached the model. Grounding each quoted figure keeps arithmetic in tested integer-cent code while allowing specific, personal coaching. Risk: the regex grounding check covers `$` amounts and `%`, not counts of months, which tools return and the prompt forbids estimating. |
| D-032 | 2026-10-30 | Accepted | Generalize approval-gated proposals to savings-goal contributions and monthly budget limits, both owner-bound, version-bound, single-use, and rechecked against the current value at approval. Add `GET /api/v1/coach/brief`, a deterministic monthly check-in that needs no model call. | Coaching often ends in a budget change, which AGENTS.md requires to be approval-gated. The check-in gives a useful, reliable first screen for the demo even without a model key. |
| D-033 | 2026-10-30 | Accepted | Remove code no client used: `GET /api/v1/demo/dashboard`, `POST /api/v1/calculations/summary`, the purchase-analyzer form, and unused chart, money, format, and dialog exports. Rename `PENNY_COUNCIL_TIMEOUT_SECONDS` to `PENNY_COACH_TIMEOUT_SECONDS` (default 45 seconds for the full tool loop). | Smaller surface area and clearer names. Existing `.env` files must rename the timeout variable, or the default applies. |
